01 · Big Picture

全景:三朵云各管什么

这个项目采用前后端分离托管:静态前端放在 Cloudflare 的全球边缘节点上,动态后端放在 AWS 的一个区域里,两者只通过 HTTPS API 通信。GitHub 则承担代码托管和自动部署的触发器。

为什么要拆开? 静态文件(构建后的 JS/CSS)不需要服务器计算,放 CDN 边缘节点就近分发,快且几乎免费;而 API 需要跑代码、连数据库,才需要真正的计算资源。这就是所谓的 JAMstack / 前后端分离部署模式。代价是两个域名之间产生了「跨域」问题——第 04 节专门讲。

一个容易忽略的知识点:前端构建时执行的是 VITE_SERVER_URL=<ApiUrl> pnpm --filter web build。这个环境变量是构建期被 Vite 直接写死进 JS 产物里的,不是运行时读取的——所以后端地址一旦变化,前端必须重新构建再发布。

三个安全组:网络层的白名单

子网决定「路由」(能不能到达),安全组决定「防火墙」(到达了放不放行)。这套模板里的三个安全组构成一条严格的信任链:

安全组 入站规则(谁能连我) 解读
lambda-sg 无入站(只有出站全放) 没人需要主动连 Lambda——它由 API Gateway 事件触发,不监听端口
db-sg 5432 端口,仅来自 lambda-sg 和 bastion-sg 数据库只认两个来源:业务代码和跳板机。注意规则引用的是「安全组」而非 IP——成员变了规则自动生效
bastion-sg 22 端口,仅来自 61.228.90.253/32(你家 IP) 全世界只有你的宽带能 SSH 上跳板机。IP 变了要更新 GitHub 变量 ALLOWED_SSH_CIDR 并重新部署
为什么私有子网还需要 NAT Gateway? Lambda 被塞进私有子网后就断网了——私有子网的路由表里没有通向 Internet Gateway 的路。但业务代码要调 api.github.com(GitHub 同步功能)!NAT Gateway 的作用是:让私有子网的机器能主动出去访问公网,但公网永远无法主动进来。单向阀门。这也是账单里最贵的一项(约 $0.045/小时)。
为什么 Lambda 要放进 VPC? 默认的 Lambda 跑在 AWS 共享网络里,根本摸不到你 VPC 内的 Aurora。把 Lambda 配置上 VpcConfig(挂进两个私有子网 + lambda-sg),它才能用内网地址直连数据库。代价就是上面说的:失去默认公网访问,需要 NAT 补回来。
03 · Request Journey

一次 API 请求的完整旅程

以你实际操作过的「点击获取账户信息」为例,追踪这个请求从浏览器到数据库再回来的每一跳:

  1. 浏览器发起 tRPC 调用
    React 组件里的 useMutation(trpc.github.syncProfile...) 最终变成一个 fetch,目标是 https://x87lulppwh.execute-api.us-east-2.amazonaws.com/trpc/github.syncProfile,带上 credentials: "include"(会话 cookie)。
  2. DNS + TLS,抵达 API Gateway
    域名解析到 AWS us-east-2 区域的 API Gateway 接入点。API Gateway 是托管服务:它终结 HTTPS、限流、然后按路由表匹配——这里只有一条 ANY / { proxy+}(万能通配),所有路径都转给同一个 Lambda。
  3. API Gateway 把 HTTP 请求「翻译」成事件,触发 Lambda
    Lambda 不是常驻服务器,而是被事件唤醒的函数。请求被打包成一个 JSON 事件对象(路径、头、体),投递给 hl-aigc-api 函数。如果此刻没有空闲实例,AWS 会现场启动一个(冷启动,约 1–3 秒);之后的请求复用热实例(几毫秒)。
  4. 适配层把事件还原成 Hono 认识的 Request
    这就是 apps/server/src/lambda.ts 全部 4 行代码的意义:export const handler = handle(app)。hono/aws-lambda 的 handle() 负责「Lambda 事件 ↔ 标准 Request/Response」的双向翻译。业务代码完全不知道自己跑在 Lambda 上——同一个 app.ts 本地开发时由 Node 直接 serve,上云时由这个适配器包一层。这是本次架构里最优雅的一处设计。
  5. Hono → tRPC → 业务逻辑
    请求依次经过 CORS 中间件、better-auth 会话解析(从 cookie 反查数据库里的 session),然后进入 tRPC procedure。syncProfile 拿着你提交的 token 去调 GitHub API——这一步的出网流量走的就是 私有子网 → NAT Gateway → Internet 那条路。
  6. Drizzle 写库(VPC 内网直连)
    Lambda 用环境变量里的 DATABASE_URL(CloudFormation 部署时用 !Sub 把集群内网地址、用户名密码拼好注入)通过 5432 端口直连 Aurora。这段流量不出 VPC,走内网,db-sg 验明来源是 lambda-sg 后放行。
  7. 响应原路返回
    Hono Response → 适配器打包成 Lambda 返回值 → API Gateway 还原成 HTTP 响应(带上 CORS 头)→ 浏览器。React Query 更新缓存,页面显示你的 GitHub 资料。全程一般 100–600ms,冷启动时更久。
Serverless 的本质交易:你放弃「常驻进程」(没有 WebSocket 长连接、有冷启动、单次执行限时 30 秒),换来「不请求不花钱、并发自动扩容、零运维」。对本项目这种低频作业应用,Lambda 计算费约等于零——真正花钱的反而是为它铺的网络(NAT)和等着它的数据库。
04 · Cross-Origin

CORS 与跨站 Cookie:两个域名之间的信任协议

前端在 hl-aigc.pages.dev,后端在 ...execute-api.us-east-2.amazonaws.com——浏览器视角这是两个毫不相干的「源」(origin)。浏览器的同源策略默认禁止 A 源的脚本读取 B 源的响应,除非 B 明确授权。这就是 CORS(跨域资源共享)解决的问题。

实际发生的头部交换

# 浏览器 → 后端(每个跨域请求自动带上)
Origin: https://hl-aigc.pages.dev

# 后端 → 浏览器(Hono cors 中间件生成,值来自环境变量 CORS_ORIGIN)
Access-Control-Allow-Origin: https://hl-aigc.pages.dev   ← 精确匹配,不是 *
Access-Control-Allow-Credentials: true                    ← 允许带 cookie
Vary: Origin

复杂请求(比如带 Content-Type: application/json 的 POST)之前,浏览器还会先发一个 OPTIONS「预检」请求探路,后端答对了才发真正的请求。这些你在 DevTools 的 Network 面板里都能亲眼看到。

登录态怎么跨域存活:三个 cookie 属性缺一不可

属性 值 为什么必须
SameSite None cookie 属于 AWS 域名,而请求发起自 Cloudflare 域名——「第三方 cookie」场景,必须显式声明 None 才会被附带
Secure true 浏览器规定:SameSite=None 必须配 Secure(仅 HTTPS),否则直接丢弃
HttpOnly true JS 读不到 cookie,防 XSS 偷会话
Safari 为什么不行? Safari 的 ITP(智能防跟踪)默认拦截第三方 cookie,不管你声明什么属性。生产环境的正规解法是让前后端共享同一个注册域(如 app.example.com + api.example.com),cookie 就成了「第一方」。本作业没买域名,所以约定用 Chrome 演示。
先有鸡还是先有蛋:部署后端时需要填前端地址(CORS_ORIGIN),可前端还没部署;部署前端又需要后端地址(VITE_SERVER_URL)。实际的解法是三步走:① 后端先用占位符 placeholder.pages.dev 上线,拿到 ApiUrl;② 用 ApiUrl 构建并部署前端,拿到真实 Pages 地址;③ 把真地址回填进 GitHub 变量,重跑一次部署刷新 Lambda 环境变量。你看到我最后重跑 workflow 就是在做第 ③ 步。

OIDC:为什么仓库里没有存任何 AWS 密钥

传统做法是把 AWS_ACCESS_KEY_ID/SECRET 存进 GitHub Secrets——一对永久有效的密钥,泄露即灾难。这个项目用的是 OIDC 联合身份,值得你重点吃透:

  1. 预先在 AWS IAM 里登记了「身份提供商」token.actions.githubusercontent.com,并创建角色 hl-aigc-gha-deploy,其信任策略写明:只信任来自 kashen336699-ks/hl-aigc 仓库 main 分支的 workflow;
  2. workflow 运行时(注意文件里的 permissions: id-token: write),GitHub 给这次运行签发一个短命的身份令牌(JWT),里面写着「我是哪个仓库哪个分支的哪次运行」;
  3. configure-aws-credentials 拿这个令牌去 AWS 换取约 1 小时有效的临时凭证,用完即废。
安全收益:没有任何长期密钥可以被偷;即使有人 fork 你的仓库或在别的分支跑 workflow,AWS 的信任策略也会拒绝。这是 2022 年后 CI 部署的行业标准做法,面试可以讲。

sam deploy 到底做了什么

SAM(Serverless Application Model)本质是 CloudFormation 的方言。sam deploy 的动作:把 apps/server/dist 打成 zip 上传到 SAM 托管的 S3 桶(resolve_s3 = true),把 template.yaml 里的占位参数替换成 GitHub Secrets/Variables 的真实值,然后让 CloudFormation 计算「期望状态 vs 现状」的差量变更集——只更新变了的资源。比如回填 CORS_ORIGIN 那次,它只改了 Lambda 的环境变量,数据库、网络全部原封不动。这就是声明式基础设施(IaC):模板是唯一事实源,改基础设施 = 改代码 + 走 git。

前端流水线(手动,两条命令)

VITE_SERVER_URL=https://x87lulppwh.execute-api.us-east-2.amazonaws.com pnpm --filter web build
npx wrangler pages deploy apps/web/dist --project-name hl-aigc --branch main

wrangler 把 dist 里的 13 个文件直传 Cloudflare,秒级分发到全球边缘节点。每次部署得到一个独立预览地址(如 f087a996.hl-aigc.pages.dev),--branch main 使它同时成为生产地址的当前版本——天然支持一键回滚。

06 · Bastion & Migration

跳板机:给「不存在于公网」的数据库开一扇带锁的门

Aurora 在私有子网里,PubliclyAccessible: false,你的电脑无论如何都直连不上——这是刻意为之的安全设计。但 schema 迁移(drizzle-kit migrate)需要真实的数据库连接,CI 里也故意不跑迁移(数据库变更风险高,应人工执行、人工确认)。解法是经典的 SSH 隧道 + 跳板机:

# 1. 建隧道:把本地 15432 端口映射到 Aurora 的 5432
ssh -f -N -L 15432:<DbEndpoint>:5432 -i ~/.ssh/hl-aigc-bastion.pem ec2-user@3.12.108.217

# 2. 迁移工具以为在连本地库,实际流量走隧道进 VPC
DATABASE_URL=postgresql://hlaigc:<密码>@127.0.0.1:15432/hlaigc pnpm -F @hl-aigc/db db:migrate

给你升级 admin 角色时,我走的就是这条隧道。这个模式(bastion / jump host)在所有「数据库不暴露公网」的正规架构里都会见到,大厂一般再进化为 SSM Session Manager 或 VPN,原理相同。

07 · Cost & Teardown

成本账单:钱到底花在哪

资源 计费方式 约成本 说明
NAT Gateway 按小时 + 流量 ~$0.045/h 最大头,只要存在就计费
Aurora Serverless v2 按 ACU 小时 ~$0.06/h 最低 0.5 ACU,闲置也不归零
跳板机 t4g.nano 按小时 ~$0.004/h 几乎可忽略
Lambda + API Gateway 按请求 ≈ $0 作业流量远在免费额度内
Cloudflare Pages 免费档 $0 静态托管免费额度充裕

合计约 $0.11/小时 ≈ $2.6/天。注意规律:Serverless 计算免费,但「常驻」的网络和数据库不免费——这是很多人对 Serverless 成本的最大误解。

演示结束后的清理清单:① sam delete 删除整个 CloudFormation 栈(VPC、NAT、Aurora、Lambda、跳板机一锅端,这就是 IaC 的另一个好处);② 删除 IAM 里的 OIDC provider 和 hl-aigc-gha-deploy 角色;③ Cloudflare Pages 免费,可留作纪念。
Recap

把知识带走:五个可迁移的模式

  1. 静态与动态分离 —— 前端进 CDN,后端进计算平台,中间用 CORS 协议握手;
  2. 公私子网 + 安全组白名单 —— 数据库永不见公网,NAT 只出不进,这套 VPC 布局是几乎所有云上架构的地基;
  3. 适配器模式解耦运行时 —— 4 行 lambda.ts 让同一份 Hono 代码既能本地跑也能上 Lambda;
  4. OIDC 免密钥部署 —— CI 不存长期凭证,信任策略精确到仓库和分支;
  5. 声明式基础设施 —— template.yaml 是唯一事实源,创建、修改、销毁都是同一份代码的不同动词。
