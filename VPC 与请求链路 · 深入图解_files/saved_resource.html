Part 1 · VPC Network

VPC:把它想成一个封闭园区

先建立心智模型,再看图。AWS 网络的每个概念都能在「封闭园区」里找到对应物,而且这个类比在细节上惊人地准确:

AWS 概念 园区类比 在本项目中
VPC 有围墙的园区,内部有自己的门牌号系统 10.0.0.0/16(6.5 万个内部门牌)
子网 Subnet 园区里的一栋栋楼 1 栋临街楼(公有)+ 2 栋内部楼(私有)
Internet Gateway 园区唯一的正门 hl-aigc-igw
路由表 Route Table 每栋楼门口的指路牌:「去园区外 → 走哪条路」 公有楼指向正门;私有楼指向收发室
NAT Gateway 收发室:替内部楼寄快递,但不代收陌生来件 hl-aigc-nat + 固定公网 IP
安全组 Security Group 每个房间自己的门禁白名单(楼能进 ≠ 房间能进) lambda-sg / db-sg / bastion-sg
跳板机 Bastion 临街楼里的接待室:访客唯一的登记入口 t4g.nano · 3.12.108.217

两条铁律,后面所有内容都建立在这上面:

  • 私有子网里的机器没有公网地址——互联网上根本不存在能寻址到 10.0.1.x 的路,这不是「防火墙拦了你」,是「地址本身在公网无意义」;
  • 路由表管「能不能到达」,安全组管「到达后放不放行」——两道独立的关卡,必须都过。

误区一(最重要):用户的 API 请求根本不进 VPC。很多人以为请求路线是「用户 → IGW → 进 VPC → Lambda」——错。API Gateway 是 AWS 的托管服务,活在你的围墙外面;它收到请求后,通过 AWS 自己的内部机制「唤醒」Lambda 并把事件塞给它,这个调用不经过你的 IGW、路由表和安全组。你的 VPC 正门(IGW)实际上只服务两件事:NAT 的出网流量、你 SSH 跳板机的流量。所以就算把 IGW 的进方向堵死,API 照样能用。

SSH 隧道到底干了什么:三个视角

那条迁移命令值得拆开看懂,因为「本地端口转发」是你以后一定会反复用到的技能: 

ssh -f -N -L 15432:<Aurora内网地址>:5432 -i ~/.ssh/hl-aigc-bastion.pem ec2-user@3.12.108.217
#        └── 含义:在我本机开一个 15432 端口;凡是发给它的字节,
#            都通过这条 SSH 加密连接搬到跳板机,由跳板机代我连 Aurora 的 5432

同一时刻,三方看到的世界完全不同——这就是隧道的精妙之处:

视角 它以为发生了什么
psql / drizzle(你本机的工具) 「我在连一个本地数据库 127.0.0.1:15432」——它完全不知道 AWS 的存在
公网上的观察者 只能看到你和 3.12.108.217:22 之间一条加密的 SSH 流,看不出里面装的是数据库流量
Aurora 「有个来自跳板机内网 IP 的客户端在连我」——它甚至不知道你的 Mac 存在
为什么 CI 不跑迁移、非要人肉走隧道?①网络上 GitHub 的 runner 不在白名单里,进不来;②更重要的是设计取舍:schema 变更是高风险操作(删列、锁表),刻意保留「人工执行、人眼确认」这道闸门。这不是偷懒,是常见的工程决策。

沿途每一站在做什么(对照上图编号)

  1. 01–02 · 静态加载,AWS 全程没参与
    页面本身来自 Cloudflare 离你最近的边缘节点。注意 02:后端地址 x87lulppwh... 是构建时被 Vite 烧进 JS 的,运行时改不了——这就是为什么换后端地址必须重新构建前端。
  2. 03–05 · 预检:浏览器替你「敲门问路」
    因为这是跨域的 JSON POST(非简单请求),浏览器强制先发 OPTIONS 探路。后端的应答里 Allow-Origin 必须精确等于 https://hl-aigc.pages.dev(通配符 * 不允许配合 cookie 使用)。预检通过后浏览器会缓存一段时间,不是每次都问。
  3. 06–07 · 进入 AWS:HTTP 在这里「变形」成事件
    API Gateway 是公开的托管端点(Path ①),它不跑你的代码,只做翻译和投递。Lambda 不是常驻服务器——没有空闲实例时 AWS 现场拉起一个(冷启动),所以偶尔第一下点击会慢一两秒,紧接着再点就快了。你演示时如果先手动访问一次页面「热身」,体验会更稳。
  4. 08–10 · 身份验证:cookie 不是凭证本体,数据库里的 session 才是
    cookie 里只是一个不透明的 session token;better-auth 拿它去数据库查(09,走内网 Path ②),查到未过期的会话才算登录有效。这就是为什么我把你升级成 admin 后要你重新登录——角色信息跟着会话查询走。
  5. 11–12 · 替你去 GitHub:整条链路里唯一一次「出园区」
    Lambda 在私有子网,没有公网身份,这次外呼走的是 Path ③:NAT 把源地址换成自己的公网 IP 再出正门。GitHub 看到的访问者是 NAT,不是你也不是 Lambda。你的 token 只在这一步的请求头里出现,用完即弃,不落库。
  6. 13–14 · 写库与返程
    UPSERT 语义保证「同一 GitHub 用户重复同步不产生重复记录」(你测过的那条验收标准就是这里实现的)。响应沿原路返回,浏览器校验 CORS 头后把 JSON 交给 React Query,界面更新。全程(热实例)约 300–800ms,其中大头往往是第 11 步等 GitHub 应答。
把两张图串起来:这次请求用到了四条路径中的三条——用户进来走 Path ①,查会话/写数据走 Path ②,调 GitHub 走 Path ③。唯独 Path ④(跳板机)不在请求链路上,它是给「人」用的运维通道。如果你能独立说出「为什么第 11 步需要 NAT 而第 09 步不需要」,这两个知识点就算真正掌握了。

自测五题(答案点开看)

1. 用户的 API 请求会经过 Internet Gateway 吗?

不会。请求终点是 VPC 外的 API Gateway 托管端点,Lambda 由 AWS 内部机制触发。IGW 只承载 NAT 出网流量和你 SSH 跳板机的流量。

2. 把 NAT Gateway 删掉,哪个功能最先坏?怎么坏?

GitHub 同步。第 11 步 Lambda 出不了网,请求会挂起直到 30 秒超时。而登录、Dashboard、字段管理照常工作——它们只用内网的 Path ②。

3. 为什么 psql 连 127.0.0.1:15432 却能操作千里之外的 Aurora?

SSH 本地端口转发:ssh 在本机监听 15432,把收到的字节加密搬运到跳板机,由跳板机在 VPC 内网代连 Aurora 的 5432。psql 全程以为自己在连本地库。

4. db-sg 的放行规则里写的不是 IP,而是另外两个安全组的 ID,好处是什么?

成员制白名单:未来 Lambda 扩容、换网卡、IP 变化都无所谓——只要它还挂着 lambda-sg 这个「工牌」,规则自动生效,不用维护 IP 清单。

5. 为什么明明只有一个数据库实例,却要两个私有子网?

RDS 的硬性规定:DBSubnetGroup 必须覆盖至少两个可用区,即使单实例也要为故障转移预留位置。所以 10.0.2.0/24 里现在几乎是空的,但必须存在。
